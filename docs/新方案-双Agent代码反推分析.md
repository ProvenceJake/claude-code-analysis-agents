# 新方案：Claude Code CLI 双 Agent 代码反推分析闭环

## 1. 方案定位

本方案不再做复杂 WebUI 和多层多 Agent 编排，而是收敛成一个更轻、更可控的 Claude Code CLI 工作流。

核心结构是：

- 一个 Claude Code CLI 会话作为执行环境
- 一个总 Agent 作为监控与调度者
- 两个子 Agent 负责具体工作
  - 代码调研与产出 Agent
  - 审查与打回迭代 Agent

目标是从“网页表现 + 代码实现”中反推出系统能力、业务实体、功能逻辑、业务规则、外部系统依赖、后台任务和权限模型，并把前后端规则提取成可复用的 JS 规则代码，最终形成一个可用于交接、汇报、重构和二次开发的 HTML 交付物。

## 2. 架构总览

```text
Claude Code CLI
└── 总 Agent：监控与调度
    ├── 子 Agent 1：代码调研与产出 Agent
    │   ├── 阅读网页、路由、前端代码
    │   ├── 阅读后端入口、服务、模型、任务
    │   ├── 归纳功能、实体、权限、外部系统
    │   ├── 提取前后端业务规则
    │   └── 生成 HTML 报告与 JS 规则代码
    │
    └── 子 Agent 2：审查与打回迭代 Agent
        ├── 校验结论是否有代码证据
        ├── 校验功能链路是否完整
        ├── 校验是否遗漏后台任务、权限、外部依赖
        ├── 校验规则抽取和 JS 代码是否准确
        ├── 校验表达是否面向交接和业务理解
        └── 不通过则打回子 Agent 1 重做
```

## 3. 三个角色的职责

### 3.1 总 Agent：监控与调度

总 Agent 不直接写最终结论，而是负责控制流程。

职责：

- 接收用户指定的项目路径和分析目标
- 明确本轮分析范围
- 调用代码调研与产出 Agent
- 将产出交给审查与打回迭代 Agent
- 根据审查结果决定是否继续迭代
- 记录每轮问题、修改点和最终采纳版本
- 在审查通过后输出最终文档清单
- 如果仍有不确定内容，必须继续打回迭代，直到不确定项清零

总 Agent 的判断原则：

- 没有代码证据的结论不能通过
- 只分析前后端调用关系不能通过
- 没有业务规则、后置事件、依赖关系的功能分析不能通过
- 没有权限模型、后台任务、外部系统分析不能通过
- 没有从前端和后端提取规则，或没有把规则转成 JS 代码不能通过
- 仍然存在不确定项不能通过
- 使用“可能、疑似、待确认、未确定”等表达替代证据不能通过
- 文档只适合开发人员阅读不能通过

### 3.2 子 Agent 1：代码调研与产出 Agent

这是生成型 Agent，负责真正查代码、看网页结构、整理证据并写分析文件。

职责：

- 扫描项目结构
- 识别前端页面、路由、组件、菜单和交互入口
- 识别后端接口、控制器、服务、模型、数据库表和任务
- 提取系统功能地图
- 提取实体与实体关系
- 对重点功能逐一做功能逻辑分析
- 从前端校验、后端校验、审批判断、状态流转、权限判断、后台任务中提取规则
- 将抽取出的规则转成可读、可测试、可复用的 JS 规则代码
- 识别外部系统依赖
- 识别后台任务和隐含业务逻辑
- 识别权限模型和权限矩阵
- 将所有结论绑定代码路径和证据

产出要求：

- 每个重点功能必须有前端入口和后端入口
- 每条业务规则尽量有代码证据
- 每条规则必须说明前端来源、后端来源、适用场景、输入、输出和 JS 实现
- 每个实体必须说明来源和关系
- 每个外部系统必须说明调用方式和调用时机
- 每个后台任务必须说明触发方式、处理对象和业务影响
- 权限模型必须说明角色、资源、操作和控制点

### 3.3 子 Agent 2：审查与打回迭代 Agent

这是检验型 Agent，负责审查子 Agent 1 的产出。

职责：

- 检查分析是否覆盖用户要求的所有部分
- 检查代码证据是否真实、充分、能支撑结论
- 检查是否把技术结构误写成业务逻辑
- 检查是否遗漏后台任务、权限、外部系统
- 检查重点功能是否覆盖完整链路
- 检查规则抽取是否覆盖前端和后端，JS 规则代码是否能表达原始逻辑
- 检查是否仍存在未解决的不确定项；只要存在就必须打回
- 检查表达是否清晰、适合业务交接和汇报
- 生成明确的打回意见

审查结果只有两种：

- `通过`：允许进入最终交付
- `打回`：必须列出问题清单，交给子 Agent 1 重新分析

## 4. 闭环流程

```text
1. 用户指定项目路径
2. 总 Agent 定义分析范围
3. 子 Agent 1 查代码并输出分析文件
4. 子 Agent 2 审查分析文件
5. 如果不通过：
   - 子 Agent 2 输出打回清单
   - 总 Agent 将问题交回子 Agent 1
   - 子 Agent 1 按问题补证据、补链路、补文档
   - 如果问题属于不确定内容，必须继续查前端、后端、配置、数据模型、任务、接口或调用链，直到不确定项清零
6. 如果通过：
   - 总 Agent 汇总最终文档
   - 输出可交付结果
```

这个流程不需要人工填写迭代轮数。每次产出后都必须审查，审查不通过就继续打回。只要仍然存在不确定内容，就不能进入最终交付，必须继续迭代，直到完全优化好。

如果关键证据无法获取，总 Agent 记录已查过的位置和需要补充的资料，并将任务标为未完成。补齐证据后，从未解决项继续复审。

## 5. 触发方式

使用提示词文档第 5 节启动本方案。Claude Code 提供的动态工作流功能也可用于辅助调研或编排，具体支持范围见 [Claude Code 官方文档](https://code.claude.com/docs/en/workflows)。

### 5.1 `/deep-research`

内置工作流 `/deep-research <问题>` 用于汇总公开网页的资料。完成外部调研后，回到双 Agent 主流程，使用仓库中的证据核实项目结论。

### 5.2 提示词包含 `workflow` 或 `ultracode`

动态工作流可用时，可明确要求 Claude 生成工作流脚本或执行计划。需要按本方案运行时，在请求中指定两个子 Agent、复审条件和报告结构。

建议用途：

- 将一次性分析任务转成可复用流程
- 自动拆分总 Agent、产出 Agent、审查 Agent 的任务边界
- 自动生成 HTML 交付物结构和审查步骤
- 让后续项目可以按同一套流程复用

示例：

```text
workflow
请为当前项目生成“双 Agent 代码反推分析闭环”的执行脚本。
要求一个总 Agent 监控两个子 Agent：
1. 代码调研与产出 Agent
2. 审查与打回迭代 Agent
输出一个 `analysis-report.html`，所有分析结果合并在一个页面中。
```

或：

```text
ultracode
请把本次代码反推需求分析拆成可执行工作流。
要求自动查代码、写文档、审查、打回、迭代，直到通过。
```

### 5.3 `/effort ultracode`

适合让 Claude 根据任务复杂度智能判断是否启动完整工作流。

建议使用场景：

- 不确定项目复杂度
- 希望 Claude 先评估再决定是否进入完整闭环
- 希望小项目走轻量流程，大项目自动进入深度流程

触发示例：

```text
/effort ultracode
请先评估当前项目复杂度。
如果只是小项目，执行轻量版双 Agent 分析。
如果项目存在多模块、多角色、审批流、后台任务、外部系统或复杂权限，则启动完整 workflow。
```

### 5.4 推荐触发策略

| 场景 | 推荐触发方式 | 说明 |
|---|---|---|
| 小项目试跑 | 普通启动提示词 | 快速验证输出结构 |
| 正式项目分析 | 启动提示词 | 使用两个子 Agent 执行生成与复审 |
| 补充公开资料 | `/deep-research <问题>` | 汇总与项目分析相关的外部信息 |
| 想复用流程 | `workflow` | 生成可重复执行的工作流脚本 |
| 高复杂代码仓库 | `ultracode` | 在支持的会话中请求动态工作流 |
| 不确定复杂度 | `/effort ultracode` | 先评估，再自动选择流程深度 |

## 6. 最终输出要求

最终只交付一个 HTML 文件：

```text
analysis-report.html
```

允许 Agent 在执行过程中使用临时笔记或草稿，但最终交付给用户的结果只能是一个 HTML。

HTML 必须包含以下页面或章节：

```text
1. 分析总览
2. 功能地图
3. 实体关系分析
4. 功能逻辑分析
5. 外部系统对接分析
6. 后台任务分析
7. 权限模型分析
8. 规则抽取与 JS 规则代码
9. 代码证据索引
10. 审查记录与迭代过程
```

HTML 要求：

- 单文件交付，CSS 和交互脚本内嵌
- 不依赖外网资源
- 支持目录导航
- 支持章节折叠或锚点跳转
- 表格清晰可读
- 代码证据路径可复制
- JS 规则代码以代码块展示，并附输入输出说明和测试样例
- 明确展示审查是否通过、打回轮次和修正点
- 明确展示不确定项清零说明；最终报告中不得保留未解决的不确定项
- 面向交接、汇报和二次开发，不只是开发者内部笔记

## 7. 输出要求详解

### 7.1 功能地图

AI 需要从网页和代码中提取系统的功能模块和能力地图。

需要说明：

- 一级模块
- 二级功能
- 页面入口
- 菜单入口
- 前端路由
- 前端组件
- 后端接口
- 后端服务
- 涉及实体
- 涉及权限
- 功能之间的依赖关系

建议表格：

| 一级模块 | 功能名称 | 能力说明 | 页面入口 | 前端代码 | 后端入口 | 核心实体 | 依赖功能 | 权限点 |
|---|---|---|---|---|---|---|---|---|

### 7.2 实体关系分析

分析系统涉及的所有业务实体，以及实体之间的关系。

需要说明：

- 实体名称
- 实体含义
- 对应表、模型或接口对象
- 关键字段
- 实体之间的一对一、一对多、多对多关系
- 实体生命周期
- 哪些功能创建、修改、审批、归档或消费该实体

建议表格：

| 实体 | 业务含义 | 代码/表来源 | 关键字段 | 关联实体 | 关系类型 | 被哪些功能使用 |
|---|---|---|---|---|---|---|

### 7.3 功能逻辑分析

对每个重点功能逐一分析。

每个功能必须包含以下部分：

#### 1. 基本信息

- 功能名称
- 所属模块
- 业务目标
- 使用角色
- 触发入口
- 输出结果

#### 2. 前后端入口

- 页面路径
- 路由路径
- 前端组件
- API 请求
- 后端 Controller 或 Handler
- Service 或 Domain 逻辑
- 数据模型或数据库表

#### 3. 业务流程

说明用户从进入页面到完成业务动作的完整流程。

需要覆盖：

- 页面加载
- 数据初始化
- 用户填写或选择
- 提交动作
- 前端校验
- 后端校验
- 数据处理
- 审批或流转
- 状态变化
- 返回结果

#### 4. 业务规则

说明代码中体现出来的业务规则。

包括：

- 必填规则
- 数据范围规则
- 状态流转规则
- 角色限制
- 配置依赖
- 时间规则
- 金额或数量规则
- 审批触发规则
- 异常处理规则

#### 5. 后置事件

说明功能完成后会触发什么后续影响。

包括：

- 状态更新
- 消息通知
- 审批流触发
- 额度变更
- 定时任务处理
- 外部系统同步
- 统计数据刷新

#### 6. 功能依赖分析

说明该功能依赖哪些配置、基础数据、权限或前置功能。

包括：

- 基础配置依赖
- 组织人员依赖
- 字典/枚举依赖
- 审批配置依赖
- 外部系统依赖
- 后台任务依赖

### 7.4 示例：加班申请分析深度

对于“加班申请”这类功能，不能只写“用户提交加班申请，系统审批”。

需要分析到：

- 申请提交入口
- 页面字段和字段来源
- 前端校验逻辑
- 后端校验逻辑
- 审批流触发条件
- 数据保存方式
- 涉及的数据模型
- 加班申请单状态变化
- 依赖的考勤类型
- 依赖的班次
- 依赖的考勤方案
- 是否依赖人员职级
- 是否调用外部系统获取人员信息
- 审批结束后的后置事件
- 是否结合打卡时间计算真实加班时长
- 是否转调休并增加额度
- 是否存在定时任务二次计算

### 7.5 规则抽取与 JS 规则代码

AI 需要从前端和后端共同提取业务规则，并把规则转成 JS 代码。

规则来源包括：

- 前端表单校验
- 前端字段联动
- 前端按钮显隐和禁用条件
- 前端路由、菜单、权限判断
- 后端参数校验
- 后端业务校验
- 后端状态机或状态流转
- 审批流触发条件
- 外部系统调用前后的适用规则
- 后台任务中的计算规则
- 数据库约束、枚举、字典和配置表

每条规则必须说明：

- 规则编号
- 规则名称
- 所属功能
- 业务含义
- 前端来源
- 后端来源
- 适用场景
- 输入字段
- 输出结果
- 异常提示
- 原始代码证据
- JS 规则代码
- 测试样例

建议规则表：

| 规则编号 | 规则名称 | 所属功能 | 业务含义 | 前端证据 | 后端证据 | 输入 | 输出 | JS 函数 |
|---|---|---|---|---|---|---|---|---|

JS 规则代码要求：

- 以纯函数为主，避免依赖页面或框架上下文
- 函数名使用业务语义命名
- 入参使用对象，便于表达复杂业务上下文
- 返回结构统一，至少包含 `passed`、`code`、`message`、`details`
- 保留来源注释，标明对应前端和后端证据
- 如果原始规则依赖数据库或外部系统，JS 代码中用入参表达依赖结果，不直接伪造接口调用
- 对无法完全还原的规则，必须继续回查前端、后端、配置、数据库、后台任务、外部接口和调用链；在清零前不得通过审查

推荐 JS 规则函数格式：

```js
/**
 * 规则：<规则名称>
 * 来源：
 * - 前端：<文件路径/组件/函数>
 * - 后端：<文件路径/接口/服务/函数>
 * 适用场景：<功能和触发时机>
 */
function validateRuleName(context) {
  const {
    form,
    user,
    config,
    externalData,
    currentState
  } = context;

  if (!form.requiredField) {
    return {
      passed: false,
      code: "REQUIRED_FIELD_MISSING",
      message: "必填字段不能为空",
      details: { field: "requiredField" }
    };
  }

  return {
    passed: true,
    code: "OK",
    message: "校验通过",
    details: {}
  };
}
```

推荐测试样例格式：

```js
const cases = [
  {
    name: "缺少必填字段时不通过",
    input: { form: {}, user: {}, config: {} },
    expected: { passed: false, code: "REQUIRED_FIELD_MISSING" }
  },
  {
    name: "字段完整时通过",
    input: { form: { requiredField: "value" }, user: {}, config: {} },
    expected: { passed: true, code: "OK" }
  }
];
```

对于“加班申请”这类功能，规则代码需要覆盖：

- 提交必填校验
- 加班时间范围校验
- 班次和考勤方案依赖校验
- 适用职级校验
- 审批流触发规则
- 审批通过后的真实加班时长计算规则
- 转调休额度增加规则

注意：JS 代码是对原系统规则的可执行表达，不是重新设计一套新规则。

### 7.6 外部系统对接分析

分析当前系统依赖或调用的外部系统，以及依赖方式和时机。

需要说明：

- 外部系统名称
- 业务用途
- 调用方向
- 调用方式
- 调用时机
- 接口路径
- 认证方式
- 请求参数
- 响应数据
- 错误处理
- 重试机制
- 数据同步周期
- 同步对象

示例：

- 通过 API 调用 NCC 系统获取职级信息
- 获取时机：提交加班申请时进行适用职级规则校验
- 需要分析接口路径、认证方式、接口参数、响应字段和失败处理

另一个示例：

- 人员数据通过 FDI 方式对接
- 需要分析同步周期、同步对象、同步字段、落库方式和异常处理

### 7.7 后台任务分析

后台任务用于发现页面不展示但真实存在的隐含业务逻辑。

需要分析：

- 任务名称
- 触发方式
- 调度周期
- 处理对象
- 查询条件
- 执行动作
- 状态变化
- 失败重试
- 业务影响
- 对应代码入口

示例：

- 加班申请审批通过后
- 定时任务检查打卡时间
- 计算真实加班时长
- 生成调休额度
- 更新申请单或额度明细

后台任务也必须按照功能逻辑分析的格式展开，不能只列任务名称。

### 7.8 权限模型分析

AI 需要从网页和代码中提取系统权限矩阵。

需要说明：

- 角色
- 菜单权限

## 8. 质量标准

最终结果必须满足：

- 每个重点结论都有代码证据
- 每个重点功能都有前后端入口
- 每个重点功能都有业务流程、业务规则、后置事件和依赖分析
- 每个重点规则都要同时检查前端来源和后端来源，不能只看单侧代码
- 规则必须转成 JS 规则代码，并说明输入、输出、错误码、提示信息和测试样例
- JS 规则代码必须能追溯到原始代码证据，不能重新发明业务规则
- 最终报告不得留下未解决的不确定项；如果仍然不确定，必须继续迭代
- 外部系统对接不能只列名称，必须说明方式和时机
- 后台任务不能只列任务，必须分析隐含业务逻辑
- 权限模型不能只列角色，必须形成矩阵
- 文档要面向交接和汇报，不只面向开发人员
- 审查 Agent 必须能指出缺失项并打回迭代
